# Architectural Decisions Log

## ADR 001: Technology Stack & Language Selection
- **Status:** Accepted
- **Context:** Case requires building an end-to-end campaign composer with real-time streaming, asynchronous message queuing, strict rate limiting (100 msg/sec), and mock providers. Allowed backends: Go or PHP.
- **Decision:** Selected **Go** for the backend and **Vue 3 (Composition API + Tailwind)** for the frontend.
- **Rationale:** 
  - Go provides first-class concurrency primitives (goroutines, channels) ideal for high-throughput dispatching and precise token-bucket rate limiting.
  - Strong typing and lightweight footprint ensure predictable performance during bulk message processing.
  - Vue 3 with Server-Sent Events (SSE) allows responsive token streaming for campaign generation and live dashboard metric updates without heavy WebSocket overhead.

## ADR 002: SQLite with a Pure-Go Driver
- **Status:** Accepted
- **Context:** Local development and `make test` must work without installing or running a database server. The primary dev machine is Windows, where CGO-based drivers require a separate C toolchain.
- **Decision:** Use **SQLite** via **`modernc.org/sqlite`** (pure Go, registers as driver `"sqlite"`), behind `database/sql`.
- **Rationale:**
  - Zero setup: no server, no gcc, identical behaviour on Windows/macOS/Linux and in a `CGO_ENABLED=0` Docker image.
  - Per-connection settings (`foreign_keys`, `busy_timeout`) are applied by a small `driver.Connector` wrapper on **every** pooled connection, not once after `Open`; a test holds several connections at once to prove it. The wrapper uses only `database/sql/driver` interfaces, so swapping drivers is a one-line change.
  - WAL journal mode allows dashboard reads while workers write.
- **Trade-offs:** SQLite has a single writer. Acceptable for the case's volume (a few thousand recipients, 100 msg/s per channel); `busy_timeout` absorbs short contention. Postgres would be the next step for multi-instance deployment.

## ADR 003: Storage Conventions
- **Status:** Accepted
- **Decision:**
  - **Timestamps** are stored as TEXT in fixed-width UTC (`YYYY-MM-DDTHH:MM:SSZ`), converted explicitly in the repository rather than by the driver. Fixed width makes lexicographic order equal chronological order, so segment filters such as `cart_last_active_at >= ?` use plain indexes and never depend on driver time formats.
  - **Booleans** are `INTEGER 0/1`; **enums** (`channel`, campaign/message/dispatch `status`) are guarded by `CHECK` constraints mirroring `internal/domain`.
  - **`dispatch_logs` has `UNIQUE(campaign_id, user_id, channel)`**, the same tuple as the provider idempotency key (`campaign_id:user_id:channel`). "The same person never gets the same message twice" is therefore enforced by the database, not only by application logic.
  - `campaign_messages` enforces "email has a subject, SMS never does" with a `CHECK`.
  - `total_spend` is `REAL` (TRY): it is a segmentation attribute compared with thresholds, not a ledger balance.
  - Schema is an embedded, idempotent `schema.sql` (`CREATE ... IF NOT EXISTS`); a migration tool is deferred until the schema needs to evolve.

## ADR 004: Deterministic, Cohort-Based Seed Data
- **Status:** Accepted
- **Context:** The seed must make the sample brief ("son 30 günde sepetine ürün ekleyip alışveriş yapmayan İstanbul'daki kullanıcılar") testable, including permission filtering.
- **Decision:** `cmd/seed` generates 3,000 users (configurable) from explicit cohorts instead of uniform randomness:
  - **True positives (~22%)**: İstanbul, cart activity in the last 30 days, no purchase in the last 30 days.
  - **Near misses**, each failing exactly one condition: converted after carting, cart older than 30 days, never used the cart, and the same abandoned-cart behaviour in other cities.
  - **Ambiguous case**: purchased within 30 days, then left a newer cart. Excluded by the strict reading of the brief; documents a real interpretation choice the segment prompt must make.
  - Every cohort contains SMS-only, email-only and both-channel opt-outs.
- **Rationale:**
  - A fixed RNG seed makes the dataset reproducible; dates are relative to run time so "last 30 days" stays meaningful.
  - `seed.MatchesSampleBrief` is a Go reference oracle. Segment-engine tests can compare their SQL results against it (verified: SQL and oracle both return the same count).
  - Emails use RFC 2606 reserved domains (`example.com/.net/.org`), so no generated address can belong to a real mailbox.
  - Canonical city spelling is `İstanbul`; the segment validator must normalise LLM output (`Istanbul`, `istanbul`) to it.
  - The command is idempotent (skips when users exist, `-reset` to reseed), so it can run on every `docker compose up`.

## ADR 005: Safe Segment Engine & AST Validation (Zero Raw SQL from LLM)
- **Status:** Accepted
- **Context:** Marketers describe campaign briefs in natural language. Executing LLM-generated raw SQL directly against the database introduces severe SQL injection vulnerabilities and unpredictable query execution.
- **Decision:** 
  - Constrained Claude to output a structured JSON Abstract Syntax Tree (AST) using Anthropic Tool Calling / Structured Output.
  - Built an in-engine whitelist validator in Go that only permits known attributes (`city`, `age`, `total_spend`, `cart_last_active_days`, `has_purchased_since_cart`) and comparison operators (`EQUALS`, `LESS_THAN_OR_EQUAL`, `IN`, etc.).
  - Implemented custom Turkish character normalization (case folding for I/İ/ı, diacritics, and 81 city aliases) to handle inputs safely without raw text matching.
  - Parameterized SQL compiler builds queries (`?`) strictly from internal Go constants, ensuring placeholder and argument counts match under fuzz testing.
  - Implemented `MockLLMClient` returning deterministic ASTs for zero-cost automated unit and integration tests without external API dependencies.

## ADR 006: Campaign Message Composer — Structured Output, Streaming & Validation
- **Status:** Accepted
- **Context:** Claude writes SMS and e-mail (subject + body) for a brief; the UI must show the text as it is generated, and nothing that breaks channel rules may reach approval or dispatch.
- **Decision:**
  - **Forced tool call** `emit_campaign_messages` with exactly `sms_content`, `email_subject`, `email_body`. The final tool input is decoded strictly (unknown/duplicate keys, non-strings, trailing data rejected). System prompt and JSON Schema are generated from the validator's limits and variable whitelist, so they cannot drift apart.
  - **Two-layer streaming:** the LLM client exposes `<-chan StreamEvent` with raw `input_json_delta` fragments; an incremental JSON field extractor turns them into per-field `MessageChunk{delta}` events (robust to fragments split inside escapes, surrogate pairs and UTF-8 sequences). Deltas are display-only; the `done` event carries the validated draft, which the UI must use instead of the streamed text. `composer.WriteSSE` relays chunks over Server-Sent Events.
  - **Validator** counts Unicode code points (not bytes) and enforces SMS ≤ 160 / subject ≤ 80 both on the template as written and on an estimated rendered length (`{{first_name}}` ≈ 10). It reports every issue at once (field, stable code, message). Subjects must be single-line (header injection); control and bidi-override characters are rejected; the e-mail body is Markdown or a small whitelisted HTML subset with balanced tags and `https/http/mailto` links only.
  - **Bounded self-repair:** an invalid attempt is sent back once with the issues (`MaxAttempts = 2`). If it still fails, a `RejectedError` carries the last attempt so the marketer can fix it by hand — the human stays in control rather than the system looping.
  - **Renderer** fills `{{variables}}` from `domain.User` in a single pass (user data is never re-parsed as a template), cleans and caps values, escapes per format, and re-checks the hard limits on the real text, because a real name can exceed the estimate.
  - **Persistence:** `Message.CampaignMessages` maps to `domain.CampaignMessage`; `CampaignRepository.SaveDraftMessages` writes SMS subjects as `NULL` (the schema CHECK rejects `''`) and refuses to change campaigns that left `draft`.
- **Trade-offs / not done:**
  - SMS length follows the case's 160-character rule. Real carriers bill by encoding (GSM-7 vs UCS-2; most Turkish letters force UCS-2 with 70-char segments); a segment counter is a natural next step.
  - The HTML check is a purpose-built whitelist tokenizer on the standard library rather than `golang.org/x/net/html`, to keep zero new dependencies. It rejects anything it does not understand instead of sanitising.
  - The Anthropic transport is duplicated between `segment` and `composer` (~60 lines); extracting a shared `internal/llm` client is deferred until a third caller appears.

## ADR 007: Dispatch Engine — Claim-Before-Send, Strict Per-Channel Rate Limit, Bounded Retries
- **Status:** Accepted
- **Context:** Approved campaigns are delivered asynchronously to a mock provider that behaves like a real gateway (~10% `429` with `Retry-After: 1`, ~5% `500`, 10-30 ms latency). The case requires ≤ 100 msg/s per channel, no duplicate delivery to the same person, no delivery without channel permission, and live progress for the dashboard.
- **Decision:**
  - **Mock provider** (`internal/provider`, standalone binary `cmd/mock-provider`): `POST /v1/sms/send`, `POST /v1/email/send`, `GET /v1/stats`, `/healthz`. Failure injection happens before any processing (nothing is accepted on a 429/500, so retrying is always safe). It enforces the `Idempotency-Key` header: the same key returns the original `message_id` (`200`, `Idempotent-Replayed: true`), the same key with a different payload is `409`. It also validates E.164 / e-mail, SMS ≤ 160 and subject ≤ 80 code points, so a limit bug in our code would surface as `422` in tests.
  - **Claim before send.** Planning inserts one `pending` `dispatch_logs` row per delivery *before* the provider is called: `INSERT ... SELECT ... FROM users WHERE id = ? AND opt_in_<channel> = 1 ON CONFLICT (campaign_id, user_id, channel) DO NOTHING`. Only the caller whose insert affected a row may send. Rows move `pending → sent | failed` with `UPDATE ... WHERE status = 'pending'`, so a final state is never overwritten.
  - **Idempotency key `campaign_id:user_id:channel`** on every attempt. The claim prevents a second *logical* delivery; the key prevents a second *physical* one when the outcome of an attempt is unknown (timeout after the provider accepted, crash between accept and `MarkSent`). Retries and `Resume` reuse the key and get the original result back.
  - **Permission checked twice:** on the loaded user (`domain.User.CanReceive`) and inside the claim SQL, so a user who opts out between audience resolution and sending is not claimed. Pending rows of users who opted out before a resume are closed as `failed`, never sent.
  - **Rate limiter** (`dispatch.Limiter`, one per channel, shared by all campaigns, every attempt including retries takes a slot): a token bucket (rate = limit/window, burst 10) for smooth pacing, plus a sliding-window log of the last 100 grant times — a grant is issued only when the 100th previous grant is at least one window old, which bounds *any* window, not just the average. Implemented on the standard library instead of `golang.org/x/time/rate` because a token bucket alone admits `limit + burst` requests in some windows, and the log is what makes the cap hard; no new dependency is needed. The enforced window is 1 s + 50 ms (`RateSafetyMargin`, ≈ 95 msg/s) so the cap also holds as observed by the provider after network/scheduling jitter; the end-to-end test asserts it on the provider's arrival timestamps.
  - **Retries:** `429`, `408`, `5xx` and transport errors are retried at most **3** times (4 attempts) with exponential backoff and *equal jitter* (`[exp/2, exp)`, base 200 ms, cap 5 s) — unlike full jitter it never retries immediately. `Retry-After` (seconds or HTTP-date, capped at 30 s) is a floor, plus up to one base of jitter so workers that were throttled together do not return together. Other `4xx` fail at once. A per-attempt timeout (5 s) bounds a hung connection.
  - **Worker pool:** per run and channel, 16 goroutines read a shared queue; channels proceed in parallel. Backoff sleeps happen inside the worker (simple, bounded by the pool size; at ~10% 429 roughly 10 workers sleep at a time, so 16 sustain the limit).
  - **Lifecycle:** `Start` requires `approved` and moves to `sending` with a compare-and-set (`UPDATE ... WHERE status = 'approved'`), so two clicks or two processes cannot both start a campaign. The run ends as `completed` (or `failed` when nothing could be delivered). A cancelled context (shutdown) leaves the campaign in `sending`; `Resume` is an explicit operation that re-sends pending rows with the same key and skips finished ones. Final DB writes use `context.WithoutCancel`, so a message the provider accepted is recorded even during shutdown.
  - **Tracking:** lock-free per-channel counters (`total`, `processed`, `sent`, `failed`, `retried` = retry attempts, plus `pending`, `opted_out`, `skipped`), exposed as `GET /api/campaigns/{id}/dispatch` and an SSE stream `/dispatch/stream`. Without a live run the numbers are aggregated from `dispatch_logs` in one indexed query. `/healthz` reports the provider but only the database decides 503.
  - **Schema version 2** (`PRAGMA user_version`): `dispatch_logs` gains `pending`, `last_error`, `created_at`, `updated_at` and `CHECK (status <> 'sent' OR sent_at IS NOT NULL)`. SQLite cannot alter a CHECK in place, so `Migrate` rebuilds a v1 table in one transaction (rename, recreate from `schema.sql`, copy, drop), keeping `schema.sql` the single source of the DDL. `domain.ErrNotFound` / `ErrStatusConflict` are now domain sentinels so use cases can match them without importing the repository.
- **Trade-offs / not done:**
  - Planning claims and renders the whole audience in memory before sending: fine for thousands of recipients and gives an exact `total` up front; millions would need a streaming planner with a durable queue (e.g. Postgres `SKIP LOCKED` or a broker) instead of in-process channels.
  - A `429` slows only the message that received it, not the whole channel. With random 429s (as in the mock) a channel-wide pause would cut throughput for no reason; a provider with real quota-based 429s would warrant an adaptive limiter (AIMD).
  - Rendering must be deterministic per user: if a user's name changes between an interrupted run and `Resume`, the provider answers `409` for the reused key and the delivery is closed as `failed` (never sent twice).
  - ~~The campaign API does not persist the approved segment rule yet~~ — resolved in ADR 008/009: `campaigns.segment_rule` stores it, and `POST /api/campaigns/{id}/dispatch` resolves the audience from it (`IDAudience` over `segment.Engine.MatchingIDs`).

## ADR 008: Derived Segment Attributes in a SQL VIEW (`v_users_segment`)
- **Status:** Accepted
- **Context:** The segment whitelist (ADR 005) exposes `cart_last_active_days` and `has_purchased_since_cart`, but `users` stores timestamps (`cart_last_active_at`, `last_purchase_at`, ADR 003). Both attributes depend on *now*, so storing them would make them wrong a day later (or require a nightly job). Until now the segment tests used their own fixture table with those columns, and the engine could not run against the real database.
- **Decision:**
  - `schema.sql` defines **`v_users_segment`** (schema **version 3**), and `segment.DefaultRegistry.Table` points at it. The view exposes `id`, `city`, `age`, `total_spend`, `opt_in_sms`, `opt_in_email` and:
    - `cart_last_active_days` = whole days since the last cart activity, **rounded up**, computed in integer seconds (`(strftime('%s','now') - strftime('%s', cart_last_active_at) + 86399) / 86400`), clamped at 0 for future timestamps; NULL without cart activity. Rounding up makes `<= N` mean exactly "within the last N × 24 h" — floor would silently include activity up to 31 days old for "son 30 gün". Integer seconds avoid floating-point `julianday` edge cases.
    - `has_purchased_since_cart` = 1 when `last_purchase_at >= cart_last_active_at`, else 0 — also 0 without a cart, so the column is never NULL and `NOT_EQUALS` has no three-valued-logic trap. The prompt tells the model to express "has a cart" with `cart_last_active_days`.
  - The view is **dropped and recreated on every `Migrate`** (views hold no data), so a changed definition always takes effect; it is not versioned like tables. `Migrate` also adds `campaigns.segment_rule` (`TEXT`, `CHECK (json_valid(...))`) to older databases with an in-place `ALTER TABLE`; the user's existing v0 database upgrades to v3 directly.
  - **No PII in the view** (name, e-mail, phone): even a hypothetical bug in the rule compiler could not select them. The column names stay plain identifiers — the derivation lives in SQL owned by the repository, not in the registry, so `NewRegistry` can keep rejecting expressions.
  - `segment.Engine` gains `MatchingIDs` (recipient ids for dispatch) and `Validate` (re-validate a stored/edited rule).
- **Verification:** the segment tests now also run on the **real seed** (3,000 users from `seed.Generate`, inserted through the repository, queried through the view) and compare counts and id sets with a Go oracle that derives the attributes the same way; a mutation (floor instead of ceil) makes them fail. `TestSegmentViewMatchesRegistryAndHidesPII` fails if the view and the whitelist drift apart. On the user's existing `campaign.db` the reference brief matches 795 users (556 SMS, 586 e-mail opt-ins).
- **Interpretation choice (sample brief):** "sepetine ürün ekleyip alışveriş yapmayan" maps to *no purchase since the last cart activity*. This includes the seed's ambiguous cohort (bought within 30 days, then left a newer cart — ADR 004), which the seed's strict oracle `MatchesSampleBrief` (no purchase in 30 days) excludes. The test pins the relation: every strict match is in the audience, and the only extra users are exactly that cohort. The strict reading would need a `last_purchase_days` field plus an "is empty" operator; deferred.
- **Trade-offs:** a view is computed per query (a scan of `users`; trivial at 3,000 rows, indexes on `city` still help the planner). At millions of rows the derived values would move to materialised columns refreshed by the event pipeline, behind the same view name.

## ADR 009: Unified HTTP API Layer (`internal/api`)
- **Status:** Accepted
- **Context:** The frontend needs one backend for the whole flow — preview, streamed generation, approval, dispatch, live tracking, health — usable from the Vite dev server and from Docker.
- **Decision:**
  - **One standard-library `http.ServeMux`** (Go 1.22 method + wildcard patterns), no framework: `POST /api/campaigns/preview-segment`, `POST /api/campaigns/compose/stream` (SSE), `POST /api/campaigns`, `GET /api/campaigns/{id}`, `POST /api/campaigns/{id}/dispatch`, `GET /api/campaigns/{id}/dispatch`, `GET /api/campaigns/{id}/dispatch/stream` (SSE), `GET /healthz`. Handlers depend on small interfaces (`SegmentService`, `ComposerService`, `CampaignStore`, `DispatchService`), not on SQL or Anthropic.
  - **Approval = one request, re-validated server-side.** `POST /api/campaigns` takes the rule and content the marketer reviewed (possibly edited) and validates both again exactly like LLM output (segment parser → canonical JSON is stored, never the client's bytes; composer validator → `422` with every issue). Campaign + messages are written as `approved` in **one transaction** (`CampaignRepository.CreateApproved`), so a half-created campaign can never be dispatched. A rule with no reachable user is refused (`empty_audience`).
  - **Dispatch resolves recipients at dispatch time** from the stored rule (re-validated: the database is not trusted with SQL either) and starts the run on the server's lifetime context, answering `202` immediately. The same endpoint **resumes** a campaign left in `sending` by a restart (ADR 007 guarantees no duplicates); a second click gets `409 already_running`.
  - **Streams:** compose uses `composer.WriteSSE` (deltas are display-only, `done` carries the validated draft); dispatch streams `stats` snapshots every 500 ms and ends with `done`. Stats gain **`speed`** (average msg/s of the run, overall and per channel) and `elapsed_seconds`. The HTTP server has no `WriteTimeout` (streams), but bounded header/read/idle timeouts.
  - **CORS middleware:** allowed origins are echoed with `Vary: Origin` (no `*` + credentials ambiguity; the API has no cookies), preflights answered `204`/`403`. Defaults cover Vite (5173/4173), 8081 and 3000 on localhost; `CORS_ALLOWED_ORIGINS` overrides. Writes require `Content-Type: application/json`, so a cross-site form post cannot reach them without a preflight.
  - **Strict request handling:** 256 KB body limit, unknown fields and trailing data rejected (a frontend typo fails loudly instead of being ignored), one error shape `{"error": {code, message, path?, issues?}}` with stable codes, LLM transport errors logged but not returned (`502 llm_unavailable`), panics recovered to `500`.
  - **Health:** checks run in parallel with a 2 s budget; only critical ones (database, including a query on the view) return `503 unhealthy`; the provider is reported (`degraded`) but does not take the API down. `system` reports uptime, goroutines, active dispatches and the LLM mode.
  - **Configuration:** env vars with an optional `.env` (repo root or `backend/`) that never overrides the real environment. Without `ANTHROPIC_API_KEY` the server runs the mock LLMs, which answer every brief with the reference rule/content, so the full flow can be demoed offline.
- **Verification:** `TestEndToEndCampaignFlow` drives the whole flow over HTTP with the mock LLM, the mock provider at its default chaos (10% 429, 5% 500) and the 3,000-user seed, at the real rate limit (~10 s): preview counts equal a Go evaluation of the rule; streamed deltas reassemble to the validated draft; seven kinds of invalid approval store nothing; the stream shows live progress and ends `completed` with `total = sms_opt_in + email_opt_in`; the provider received only audience members with the channel's opt-in and accepted each idempotency key once. Further tests cover error mapping, resume, CORS and health; `go test -race` is clean.
- **Trade-offs / not done:** no authentication or per-user rate limiting (out of the case's scope; would sit in the same middleware chain); no campaign list endpoint yet (the dashboard tracks campaigns it created); the audience can shift slightly between approval and dispatch because "last 30 days" is relative to now — dispatch-time resolution is deliberate, since it also honours opt-outs.

## ADR 010: Frontend — Vue 3 SPA as a Thin, Validating Client of the API
- **Status:** Accepted
- **Context:** The marketer needs one screen flow for brief → audience → streamed content → human approval → live dispatch, on top of the REST/SSE API of ADR 009. The case weights the frontend at 20% and the human stays the final decision maker, so the UI must show *what the backend understood* (canonical rule, validated draft) rather than what the model typed, and must never become a second source of truth for the rules.
- **Decision:**
  - **Stack:** Vue 3 Composition API (`<script setup>`), Vite 8, Tailwind CSS v4 (CSS-first config: design tokens in `frontend/src/style.css` `@theme`), Vitest + `@vue/test-utils` + jsdom. **No router and no state library:** the five steps are one linear wizard, so a single composable (`useCampaignFlow`) is the state machine and every later step is *derived* from earlier ones (`reached`): editing the brief invalidates audience and content; once a campaign is approved the earlier steps are read-only. Tailwind v4 was chosen over v3 because v3's dependency tree (`chokidar` → `braces`/`micromatch`) carries open npm advisories, while v4 audits clean; its native binaries ship for Windows (`win32-x64-msvc` is in the lockfile).
  - **Dev topology:** Vite proxies `/api` and `/healthz` to `http://localhost:8080` (`VITE_API_TARGET` overrides), so the browser talks to one origin and CORS is not involved in development; proxy timeouts are disabled so SSE streams are not cut. `VITE_API_BASE` allows an absolute API origin for builds served without a proxy (the API's CORS allow-list already covers 5173/4173).
  - **Two stream clients, chosen by HTTP method.** The compose stream is a `POST`, which `EventSource` cannot send, so it is read with `fetch` + `ReadableStream` and a small WHATWG event-stream parser (`lib/sse.js`: LF/CR/CRLF, CRLF split across chunks, multi-line `data`, comments, UTF-8 split inside a character — all unit-tested at every split point). The dispatch stream is a `GET` and uses `EventSource`, which is closed on `done` (otherwise it reconnects forever); if the browser gives up (`CLOSED`) or the server sends `event: error`, the composable falls back to polling `GET …/dispatch` until the run is final.
  - **Deltas are display-only.** Streamed text gives the typing effect; on `done` the fields are replaced by `draft.message`, the validator-approved content, which is what review starts from. `retry` clears the fields and lists the validator's issues while attempt 2 streams. `error` with `rejected` opens the review with the last attempt so the marketer can fix it by hand (the bounded self-repair of ADR 006 ends with a human, not a loop).
  - **Client-side checks mirror, never replace, the server.** `lib/text.js` reproduces the composer's counting (Unicode code points, not UTF-16 units — `🎉` is 1; trimmed like `composer.Normalize`; the `{{var}}` scanner's malformed cases; `{{first_name}}` ≈ 10 characters) so the SMS 160 / subject 80 counters turn red at exactly the server's threshold and "Onayla ve gönder" is disabled while any field breaks a rule. Approval still goes through `POST /api/campaigns`, which re-validates everything; its `422 invalid_content` issues are shown next to the offending field and cleared when that field is edited. Model output and edits are rendered as text only (no `v-html` anywhere); the personalised preview fills whitelisted variables with a sample name and leaves unknown ones visible in red.
  - **Human-in-the-loop affordances:** the audience card shows the canonical rule in plain Turkish next to its raw `field OPERATOR value`, and can be edited as JSON and re-counted via `preview-segment {rule}` (no LLM call; the server whitelist parser decides, the client only checks it is a JSON object). Every edited field is marked "Düzenlendi" with a one-click way back to Claude's suggestion. The approval bar states the consequence (how many SMS / e-mail recipients; no send without opt-in; no duplicates).
  - **Dashboard metrics:** progress = `processed / total` (sent and failed segments), counters for sent / failed / retried / pending, and a per-channel table. The server's `speed` is the run *average*; the UI also derives an **instantaneous** per-channel rate from consecutive snapshots (Δprocessed / Δt over ~2 s) and plots it against the 100 msg/s per-channel cap, so throttling and retries are visible while they happen. Finished runs switch the gauge to the average and stop the chart at the last live sample. An `interrupted` run (restart during sending) offers "Gönderime devam et", which calls the same dispatch endpoint (resume, ADR 007); `409 already_running` simply attaches to the live stream.
  - **Health badge:** polls `/healthz` every 10 s with a 4 s timeout, pauses while the tab is hidden, and treats a `503` body as data (`unhealthy`) rather than an exception; a network failure is `unreachable`. A popover lists each check, uptime, active dispatches and the LLM mode (mock / Claude).
  - **Visual system:** cool paper/ink neutrals with an ultramarine action colour; channel identity is fixed everywhere (SMS teal, e-mail violet); green/amber/red are reserved for status and always paired with an icon and a label. Previews mimic where the message lands (a phone thread for SMS, an inbox card for e-mail). Keyboard focus is visible, focus moves to each step's heading, `prefers-reduced-motion` is respected, layouts collapse to one column on phones.
- **Verification:** `npm test` runs 61 Vitest tests without a backend: SSE parsing at every chunk boundary, counter parity cases (Turkish letters, emoji, variable estimates, malformed placeholders), rule descriptions, the API client's error envelope, the compose stream (typing → authoritative replace, retry, rejected, truncated stream, abort on unmount), the dispatch stream (instant speed, close on final, polling fallback, stale connections ignored), health polling, the whole wizard flow with a fake client (edits sent trimmed, 422 issues per field, brief change invalidates later steps, `already_running`), and component behaviour (red counter and disabled approval at 161 characters, variable insertion at the cursor, unknown variable flagged, empty audience blocks generation). The flow was also driven end to end in headless Chromium against a stub implementing the documented API contract.
- **Trade-offs / not done:**
  - The UI tracks only the campaign it created (the API has no list endpoint yet, ADR 009); a page reload loses the wizard state although the dispatch continues server-side. A `GET /api/campaigns` + `?id=` deep link would restore it.
  - The e-mail preview shows the Markdown/HTML source as text instead of rendering it; rendering would need a sanitiser matching the server's whitelist exactly, and a mismatch would show the marketer something different from what is sent.
  - No i18n layer: copy is Turkish, inline in the components. No E2E browser test in CI yet (Playwright against `docker compose` is the natural next step), and ~~no Dockerfile for the frontend~~ — resolved in ADR 011 (nginx image with the same `/api` proxy).

## ADR 011: Container Orchestration — One-Command `docker compose up`
- **Status:** Accepted
- **Context:** The case requires that an engineer who clones the repository can start the whole system — API, mock provider, seed data and frontend — with `docker compose up` and nothing else installed, and that tests run with `make test`. The primary development machine is Windows, so the setup must not depend on host paths, line endings or a host toolchain.
- **Decision:**
  - **Four services, one volume.** `mock-provider` (`:9090`), `seed` (one-shot), `backend` (`:8080`), `frontend` (`:3000`), sharing the named volume `db-data` mounted at `/data` (`DB_PATH=/data/campaign.db`). Start-up order is expressed with conditions, not sleeps: `backend` waits for `seed: service_completed_successfully` **and** `mock-provider: service_healthy`; `frontend` waits for `backend: service_healthy`. Host ports are overridable (`FRONTEND_PORT`, `BACKEND_PORT`, `MOCK_PROVIDER_PORT`) and published on `127.0.0.1` only.
  - **Seeding as a separate one-shot service**, not inside the server's start-up. `cmd/seed` is already idempotent (ADR 004: it exits when users exist), so it runs on every `up` and costs nothing after the first; the server stays free of fixture code and a seed failure stops the stack visibly (the backend never starts on an empty database). `make docker-reseed` stops the backend, runs `seed -reset` and starts it again, because "last 30 days" cohorts age with the volume.
  - **One backend Dockerfile, four targets.** A shared `deps` stage (`go mod download && go mod verify`, cached until `go.mod`/`go.sum` change) feeds `build` (`CGO_ENABLED=0`, `-trimpath -ldflags="-s -w"`, all three commands in one compile) and `test` (`go test ./...`). The runtime targets `server` (default), `seed` and `mock-provider` copy one binary each onto the same base, so each image has exactly one entrypoint and Compose needs no shared image tag (a service that only references a locally built tag is *pulled*, not built, by some Compose versions). BuildKit builds the common stages once.
  - **Alpine runtime instead of distroless.** The pure-Go SQLite driver (ADR 002) makes the binaries static, so distroless would work, but it has no HTTP client for a healthcheck; adding a probe binary or a `-healthcheck` flag to every command is more code than busybox `wget` (a few MB of image size). The runtime stage installs **no packages** (`apk add` would make every build depend on the Alpine CDN, which failed behind Docker Desktop's network on Windows): TLS roots for `api.anthropic.com` come from `ca-certificates-bundle`, already part of the Alpine base image, and no `tzdata` is needed because all timestamps are UTC (ADR 003) and nothing calls `time.LoadLocation`. User and directory setup uses busybox built-ins only. The image runs as uid `10001`, and pre-creates `/data` owned by that user — Docker copies that ownership into a fresh named volume, so the non-root seeder and server can write the database without an init container.
  - **Healthchecks use the real endpoints:** `GET /healthz` on the API (503 when the database or the segment view is broken — a provider outage is only `degraded`, ADR 009), `/healthz` on the mock provider, `/` on nginx. `wget` exits non-zero on any non-2xx, so a 503 fails the check.
  - **Frontend:** `node:22-alpine` runs `npm ci` from the committed lockfile — it already pins the `linux-x64-musl` native bindings of rolldown, lightningcss and `@tailwindcss/oxide` next to the Windows ones — then `vite build` with an empty `VITE_API_BASE` (same origin). `nginx:1.27-alpine` serves `dist/` and reverse-proxies `/api` and `/healthz` to `${API_UPSTREAM}` (default `backend:8080`, rendered by the image's envsubst template mechanism). For the two SSE endpoints the proxy disables buffering and gzip and allows a 1 h read timeout (the API also sends `X-Accel-Buffering: no`). The upstream is resolved per request through Docker's DNS (`resolver 127.0.0.11 valid=10s`) rather than once at start-up, so rebuilding only the backend — which gives it a new IP — does not leave nginx proxying to a dead address. Hashed `/assets/*` are cached for a year, `index.html` is `no-cache`, unknown paths fall back to `index.html` (SPA). The browser sees a single origin, exactly like the Vite dev proxy, so CORS never applies.
  - **Configuration:** Compose reads the root `.env` only for `${VAR:-default}` substitution; the containers get an explicit `environment:` list. `DB_PATH`, `PROVIDER_URL` and `HTTP_ADDR` are fixed by Compose (a local-dev `.env` with `localhost` URLs cannot leak into the containers), and `ANTHROPIC_API_KEY` reaches only the backend. With no `.env` at all the stack starts in mock-LLM mode.
  - **Tests without a toolchain:** `make test-docker` builds the `test` targets of both Dockerfiles, i.e. the same `go test ./...` and Vitest suites as `make test` / `make test-frontend`, with only Docker installed.
- **Verification:** `docker compose config` validates the file (merge keys, conditions, ports, volume). The frontend stages were replayed outside Docker on Linux: `npm ci` from the Windows-generated lockfile, 61/61 Vitest tests, `vite build`. The nginx template was rendered with the same envsubst rule as the official image (all defined variables; nginx's `$uri`, `$host`, … untouched), passed `nginx -t`, and was exercised against a stub upstream: SPA deep links return `index.html`, assets are served gzip-compressed with immutable caching, missing assets are `404`, `/api` POST bodies and `/healthz` are proxied, an SSE stream emitting an event every 500 ms arrived at the client at the same 500 ms cadence (no buffering), and the healthcheck command exits `0` on `200` and `1` on `503`. The mock provider binary answered its healthcheck with the Compose environment.
- **Trade-offs / not done:**
  - SQLite on a named volume ties the API to one replica (ADR 002); scaling `backend` would need Postgres and a shared queue (ADR 007). A named volume rather than a bind mount is deliberate: WAL needs shared-memory locking that NTFS/virtiofs bind mounts on Windows and macOS do not provide reliably, and it keeps the database out of the working tree.
  - Images are built locally on first `up` (a few minutes); publishing them to a registry from CI would make start-up instant but needs a CI pipeline, which is a bonus item not done yet.
  - Base images are pinned to minor versions (`golang:1.24-alpine`, `alpine:3.20`, `node:22-alpine`, `nginx:1.27-alpine`), not digests: reproducible enough for a case study while still receiving security patches; production would pin digests and update them with a bot.
  - No TLS termination and no auth in front of `:8080` / `:9090`: the API and the provider are published so reviewers can inspect them, but bound to `127.0.0.1` (Docker would otherwise publish on all interfaces). A deployment would publish only the frontend.
